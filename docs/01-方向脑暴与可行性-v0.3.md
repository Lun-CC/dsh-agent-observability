## 一、判定用的三道关

任何想法必须同时过三关，任一关不过即淘汰：

| 关 | 问题 | 判定依据 |
| --- | --- | --- |
| **存在关** | 有人做了吗 | GitHub 定向检索（受 API 限额，标"未发现"≠"不存在"） |
| **可行关** | 平台让不让做 | 已核实的 `ctx` 能力（第二节） |

### 2.2 关键能力清单

**事件（durable，可 replay）**
`session/event`（全量流）、`turn/start|end`、`step/start|end`、`tool/call|result`、
`assistant/message`（每次成功 provider 调用，含 content-less 与 max-tokens 结束）、
`assistant/attempt`（失败/重试/取消的流）、`subagent/start|end`、
`workflow/start|phase|log|end`、`workflow/agent-start|end`、`goal/changed`

**瀑布（可拦截、可改写，不只是监听）**
`tools/pre-execute`、`tools/execute`（timeout/retry/metrics 环绕）、`tools/post-execute`、
`tools/result`、`agent/pre-step`、`agent/request`、`agent/request-error`、
`agent/turn-stopping`、`system-prompt/assemble`、`llm/stream`

> `tools/pre-execute` 的返回值可以 **allow / deny / ask / transform**。
> 这意味着"拦截"是合法能力，不是 hack。多数竞品只用了监听。

**`ctx.tokenMeter.measure(session, requestHeader?)`** → `TokenMeasurement`

```ts
{
  logRevision: SessionLogOffset     // 消费了多少条 durable 事件
  baseline: TokenMeasurementBaseline // 'usage'（真实 provider 用量）或 'estimated'
  surfaceDeltaTokens: number        // 相对锚点涨落，带符号
  totalTokens: number               // 请求+响应压力
  surfaceTokens: number             // 仅 surface 的路线定价总量
  nodes: readonly { seq, tokens, heuristicTokens }[]  // ← 逐事件的定价
}
```

**每个 session event 都有独立 token 价，带 durable seq 可定位。**
v0.1 以为"token 归因"是最难的技术活，实际上服务层直接给。

**`ctx.sessionQuery`**
`listSessions()` / `readSession(id)` / `traceSession(id)`（递归子孙，subagent 树）/
`traceEvent(req)`（surface 替换链 + 引用来源）/ SQLite 全文检索

**其余相关能力**
`ctx.otel`（一方 OTel 传输，事件与 session-log 双通道）、
`spill`（工具结果超出 `maxInlineTokens` 落盘，只回 locator）、
`compaction`（`agent/pre-step` 压力触发 + `agent/request-error` 溢出触发，先剪枝后摘要）

### 2.3 这条发现改变了什么

v0.1 的护城河假设是："都得真读懂 ctx 和事件流，抄不走。"

实际情况：**数据管道已被平台商品化。** 逐事件 token 价、历史查询、lineage 追踪、
OTel 传输、全文检索，全部是一方 API。抄的人不需要"读懂"，查文档即可。

护城河不在"拿到数据"，只在两处：
1. **怎么归因**（把 LLM 调用上的花费分摊回导致它的动作，这是建模不是读取）
2. **怎么给处方**（诊断出问题后，改什么配置、改哪条指令）

### 关键几条展开

**#7 预执行拦截 —— 唯一"零解读成本"的形态**

`tools/pre-execute` 允许 deny 或 transform。于是可以：

- agent 第三次执行同一条失败命令 → 不执行，改为把前两次的错误注入回的 prompt
- agent 反复读同一个文件第 5 次 → 命中 spill locator 缓存，直接返摘要
- 单步已耗 40k token 且无产出 → force compaction

用户装上就生效，**不需要打开任何面板**。这是唯一能绕过"解读成本"规律的产品形态。

风险明确：误拦会把 agent 卡死。所以必须实现 abstain 策略，并且默认只**建议**（写一条 assistant 可见的提示）不**阻断**。可分两档，默认软档。

`cc-safety-net`(1,716★) 证明了这条路的受众量级——但它拦的是"危险"，不是"浪费"。

**#6 压缩审计 —— 受众最确定的一个**

compaction 的触发链已核实：`agent/pre-step` 看压力、`agent/request-error` 看 canonical overflow、
先可选剪枝再摘要、只在 replacement generation 前进时重试。

可测的失败模式：压缩丢了某个节点，之后 agent 又去重新获取它（重读同一文件、重跑同一命令）。
用 `readSession` 做压缩前后 surface 对比，用 `traceEvent` 的 `replacementChain` 追被替换的节点，
统计"被丢掉的节点在后续 N 步内被重新引用"的比例。

输出是一句话："第 7 步压缩丢掉了构建命令的路径，之后重读 3 次，多花 11k token。"
解读成本几乎为零，且上下文上限是普遍痛点——受众比"想复盘的人"大一个量级。

**#2 的分量**

这是唯一需要真正**建模**的：token 花在 LLM 调用上，工具只消耗时间和上下文。
"某工具花了多少钱"不是测量问题，是**分摊模型**问题——工具的返回字节如何污染后续每一次请求。

这个模型有取舍、有反例、有可讨论的边界。面试官问"你为什么这么分摊"，有真答案。
这是 v0.1 里唯一真正值钱的东西，也是唯一抄不走的。

## 五、收敛：三个决赛者

| | A. 上下文体检 + 处方 | B. 预执行拦截 | C. 压缩审计 |
|---|---|---|---|
| 一句话 | 一次会话跑完，告诉你三处浪费在哪、各改什么 | 装上就少烧，不打开面板 | 压缩丢了什么，导致后面重花多少 |
| 形态 | 结论 + 可执行修改 | 静默旁路 | 一句话结论 |
| 解读成本 | 低（是条文不是图） | **零** | 极低 |
| 受众 | 中高 | 高（参照 1,716★） | 高（上限是普遍痛点） |
| 技术难度 | 中高（需分摊模型） | 中（需 abstain 策略） | 中 |
| 智识含量 | **高**（归因模型） | 中（策略工程） | 中（对比算法） |
| 与 dsh-maze | 正面错开 | 完全错开 | 完全错开 |
| 主要风险 | 处方不准就是噪音 | 误拦卡死 agent | 依赖 compaction 默认实现细节 |

三者不互斥，A 是骨架，B 与 C 是 A 的两个"执行端"。

## 六、推荐：账单 + 处方，而不是时间轴

### 6.1 论点

v0.1 假设 agent 的钱花在"慢工具"上。核实后的判断是：
**agent 的钱花在上下文污染上。** 而污染有四条可测路径，全部落在已核实的 API 覆盖范围内：

| 污染路径 | 可测依据 | 处方 |
| --- | --- | --- |
| 未使用插件的 schema 税 | `system-prompt/assemble` + 工具目录 + 使用计数 | 停用某插件 |
| 工具结果无限回填 | tokenMeter 逐节点价 + spill `maxInlineTokens` | 调阈值 / 开 spill |
| 压缩丢关键信息 | `replacementChain` + 后续重新获取 | 调 retention / 换摘要策略 |
| 失败动作重复 | `tool/call` 序列近似重复 | 拦截 + 回注错误 |

### 6.2 产品形态

输入一次会话（或一个项目的历史会话），输出**三条结论，每条配一个可执行的修改**：

> 1. 插件 X 的工具 schema 每次请求占 1,240 token，30 天内 0 次调用 → 停用，预计省 18%
> 2. 第 4 轮起工具结果未走 spill，一次读取 42k token 常驻到结束 → `maxInlineTokens=8000`
> 3. 第 7 步压缩丢掉了文件路径清单，之后重读 3 次，多花 11k token → 提高 retention 下限

**图不是主体，是证据。** 每条结论可点开看到"从第几步开始"的时间定位——
v0.1 的那句 slogan（"从哪一步开始跑偏"）在这里兑现了，但它是折叠的，
不是首屏。首屏是三条结论。

### 6.3 为什么它同时过两关

- **若目标是产品**：受众从"想复盘的人"（87★ 量级）换成"上下文爆了的人"（上限痛点），
  且形态是账单不是报表，绕开了受众规律
- **若目标是作品**：分摊模型 + 处方库是真正的设计取舍，能答"为什么这么归因"；
  而 maze 那种"把事件画到时间轴"没有可辩论的模型

### 6.4 明确的代价

**这个方案已经从"trajectory 分析"漂移到"上下文成本诊断"。** 这是取舍，不是升级：

- 得到：受众大一个量级、零解读成本、绕开全部在位者
- 失去：v0.1 那个"行车记录仪"的纯粹直觉；以及"看 agent 怎么干活"的叙事快感

如果"行车记录仪"这个直觉本身对你有不可替代的价值，那就该选决赛者 B 或 C 单独做深，
而不是选这个合成方案。这个判断只能你下。

## 七、唯一的技术不确定性：归因只能做到静态口径

**#8 归因到"插件"这件事，只能做到静态口径。**

核查 `docs/subsystems/tools.md` 的结果：

- 注册接口是 `ctx.tools.register(definition) => () => void`，查询是 `ctx.tools.get(name, scope?)`
- 归属靠**返回的 disposer 挂在注册插件的 fiber 上**隐式表达
- 文档**没有**暴露 `tool → 注册者` 的可查询映射（grep `owner|source|bundle|origin|provenance` 无命中工具来源字段）

因此运行时无法直接问"这个 tool 是谁注册的"。可行的替代路径是**静态归属**：

1. 读各 bundle 的 `dsh.bundle` 清单与 `package.json`，拿到每个插件声明的工具名
2. 与运行时 `ctx.tools` 实际注册的工具名做集合对齐
3. 声明了但没注册 / 注册了但没声明，本身就是有价值的信号

结论：#8 **可做，但归因是静态口径**（按 manifest 声明），不是运行时血缘。
这有两层代价：
- 错报：某插件通过非 manifest 途径注册工具时会漏
- 但反过来，"清单与实况不一致"本身可以做成一条结论——`unStone/dsh-xray` 做的就是这件事，
  说明这个信号有人认，只是它没往 token 账单方向走

`system-prompt/assemble` 瀑布仍是逐请求拿到完整拼装内容的入口，
所以"某个 schema 在每次请求里占多少 token"是可测的（tokenMeter 逐节点定价），
只是"这个 schema 该记在哪个插件账上"要靠上面的静态对齐。

其余想法（#2 #3 #5 #6 #7）的能力依赖都已在文档层面核实，无此风险。
