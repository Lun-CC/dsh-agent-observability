## 3. 真正该看的那张表：星数是受众规模的函数

| 维度 | 该维度最高星 | 用户装完要做什么才能获益 |
| --- | --- | --- |
| 免登录 / 桌面外壳 | 32,266 | **什么都不用做**，装上就生效 |
| 视觉能力 | 4,375 | 发张图 |
| 安全防护 | 1,716 | 什么都不用做，后台拦截 |
| 成本计量 | 481 | 看一个数字 |
| Runtime 观测 / profiling | 218 | 看几个指标 |
| **Trajectory 可视化** | **87** | **读懂一张时间轴，再自己判断哪里错了** |

规律很清楚：**每多要求用户做一层解读，受众掉一个数量级。**

v0.1 里这句话把因果搞反了：

> "不是因为它更难所以星少，是因为做的人少、被发现得少。"

真实情况是——**做的人不少（6 个），被发现得也不少（dsh-maze 挂了 8+ 个收录徽章），
是受众本身就那么小。** 87 星不是 dsh-maze 的失败，是"愿意复盘 agent 轨迹"这件事的
人群在 2026 年 10 月只有这么点。

而 v0.1 要做的东西，恰好站在解读成本最高的一档。

这一条不改观，换任何实现方式都没用。

### 附带发现：星速

- `dsh-our-free-model`：2026-09-24 创建，27 天 32,266★ ≈ 1,195 星/天
- `T-Auto/dsh-ops`：2026-10-08 创建，13 天 3,568★ ≈ 275 星/天

这个生态的星数由**发布首周新奇效应**驱动，与留存几乎无关。
推论：在这里"做得深"换不来星，"发布时机 + 分发渠道"才换得来。

### 附带发现：验收标准写错了

主仓库 **`has_issues: false`**，`has_discussions: true`。
v0.1 第八节把"有人提 issue"当成功标准——在这个仓库上结构性无法达成。
可用替代指标：npm 周下载量、Discussions 发言、被 dshbase / dshfind / dsh-plugin-radar 收录、Star 增长曲线的**第二周存活率**。

## 4. 仍然成立的判断

- **"帮用户看懂 agent 怎么花钱"这个方向本身是对的**，需求被 481★ 的 cost-meter 侧面验证了。
- **"读 ctx 和事件流"是真门槛**，仍然挡得住三天复制——但现在证明的是"挡得住复制，挡不住没市场"。
- **贴 ctx 边缘、不深挖内核**的策略正确，developer preview 的 API 会动。
- **不做大而全平台**的原则正确，且被数据加强：这个生态里没有大而全的成功案例。
- 风险 3（"方向被抄的速度可能很快"）已经从推测变成事实——不是"可能很快"，是"已经有人做完了"。

## 5. 三个判断题，换成带数据的版本

**Q1. 第一版只做哪个维度？**

不再是三选一，因为三个都已被 dsh-maze 做过。真实可选的是：

- (a) 做 dsh-maze 的**更差版本** —— 排除
- (b) 做 dsh-maze 的**互补层**：它画"发生了什么"，没人回答"**从哪一步开始跑偏**"。
      v0.1 的一句话里写着这句，但 maze 交付的是视图不是归因。
      技术形态：动作级去重找无效循环 + 首个不可逆分叉点检测 + 前缀归因。
      这是诊断，不是视图。
- (c) 换到唯一没被专占的"插件冲突检测" —— 但已验证需求上限低（35 个命中无头部），且与 dsh-xray 语义重叠

(b) 是唯一同时满足"有空间"和"有智识含量"的选项。它也是唯一能把 v0.1 的那句话兑现的选项。

**Q2. 用户打开后第一眼看到什么？**

这个问题现在有了新的答案可能：如果做 (b)，第一眼不该是图，该是**一句话结论**——
"这场会话从第 37 步开始跑偏，之后 62% 的 token 花在重复第 31–37 步的尝试上"。
图是佐证，不是主体。这跟 dsh-maze 的产品形态正面错开。

**Q3. 什么算做成了？**

按第 3 节的结论，这个项目的目标用户上限约在百人量级。
所以"几千星"不是合格的成功定义。需要先回答第 6 节那个问题，再定指标。

## 6. 必须先回答的一个问题（v0.1 没有问）

**这是作品，还是产品？**

v0.1 第七节的协作原则透露了真实目标：面试官会问"为什么按工具维度切而不是按时间轴切"，
"答 AI 写的这一轮就结束"。也就是说，**这东西的首要用途是证明判断力，不是获取用户。**

这两个目标导出的方案完全不同：

| | 作品（面试 / 能力证明） | 产品（要用户） |
| --- | --- | --- |
| 市场饱和 | 不重要。你不是在抢 87 星 | 致命。第 3 节的天花板就是你的天花板 |
| 该选哪个维度 | 挑解读成本最高、架构最能讲的那个 → (b) 归因 | 挑受众最大、零解读成本的 → 但那是白嫖/外壳，法律与技术门槛都不合适 |
| 成功的证据 | 能讲清 40 分钟的设计取舍；有人能复述你的归因算法 | 周下载量、留存 |
| 投入产出 | 高。一个 87★ 的精致工具足以撑起技术叙事 | 存疑。参照 cost-meter，天花板 481★ |

**如果答案是"作品"，v0.1 的整个市场焦虑可以卸掉一大半**——你不需要赢，你需要深。
但如果目标是产品，第 3 节的表说明这个方向从一开始就选错了档位，应当换方向而不是优化实现。

这个判断只能你来做。它决定了后面所有事。

## 7. 技术未知项：仍未确认（v0.1 第五条，原样保留）

v0.2 只做了市场核验，**没有读源码**。下列五条依旧是猜的：

1. `ctx.on()` 的事件名与负载结构
2. session log 的落盘格式与 schema
3. subagent 调用如何嵌套记录
4. 单次任务的 token 成本能否精确归因到某一个工具调用 —— **这条现在最关键**，它决定 (b) 方案是否可行
5. 插件能否读历史 log，还是只能挂实时事件

第 4、5 条若为否，(b) 里"前缀归因"就只能做成实时旁路，产品形态要改。

读源码这件事仍然在我这边，且应该在动手写任何代码之前完成。但先等第 6 节的判断落定，
否则可能把源码读在一个已经放弃的方向上。
